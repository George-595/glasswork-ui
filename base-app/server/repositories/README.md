# server/repositories

The SQL. One factory per table group, taking a `DbExecutor` (the client, or a transaction's
`tx`); `createRepositories(db)` builds them all.

- Map rows (snake_case) to the wire records (camelCase) and back. No business rules.
- SQL must run on SQLite, Postgres and MySQL: `?` placeholders, portable types, `Number()` on
  counts and sums (drivers may return strings), and never a bound `LIMIT ?` (MySQL rejects it
  in prepared statements; inline a clamped integer instead).
- **Timestamps:** bind a `Date` (convert the wire's ISO string with `new Date(...)` at the SQL
  boundary); every row comes back with ISO-8601 UTC strings. Never compare timestamps as text in SQL.
- **Ids** are UUIDv7 strings generated by the caller (`server/lib/ids.ts`); there is no `lastInsertId`.
- **One contract suite:** `server/repositories.contract.test.ts` runs every repository's behaviour on
  SQLite (always) and on Postgres and MySQL (`npm run test:db`). A new repository method gets a case there.
- **Races are the database's job:** a claim is one `UPDATE ... WHERE id = ? AND status = 'queued'` and a
  check of `rowsAffected`; a duplicate is a unique index, not a SELECT first. Upserts are UPDATE then INSERT.
- **Platform queries** (extend the contract suite when you add one): `jobs.page` / `retry`, `outboundEmails.page` /
  `count` / `deleteCreatedBefore`, `notifications.deleteReadBefore`, `authTokens.deleteSpentOrExpired`.
- `notifications.listForUser` takes a keyset cursor (`after: { createdAt, id }`); `findForUser` is the ownership-checked read;
  `users.activeIds({ role?, exceptId? })` feeds fan-out notifications.
- **Tables:** `users`, `sessions`, `auth_tokens`, `transactions`, `audit`, `activity`, `metrics`,
  `notifications` (+ preferences), `jobs`, `outbound-emails`, `app-settings`, `files`.
- **May import:** `infra/db` types, `shared/`, `lib/`. **Never:** services, routes, http.
- `agent.ts`: `agentRepository` (saved chats: conversations and their messages, always looked up with the
  owner's id) and `savedViewsRepository` (pinned views, oldest first). Deleting a conversation is one
  `DELETE`; its messages go by `ON DELETE CASCADE`.
